# 板块成分获取与审计修复计划

日期：2026-09-06。状态：待实施。

## 目标与事实依据

解决今日推荐中 `sector_membership 40 / 145 / 0 / 20 / 0 / healthy` 暴露的跨源板块身份问题，并让审计准确区分接口可访问与成分覆盖不足。

本次已有运行记录：40 个板块逻辑请求、145 次底层尝试、20 个映射缺失、成分可用覆盖率 50%。这是单次样本，不作为修复后的固定成功率目标。

已核对代码：

- `stock_scanner.py:gather_candidates()` 将 `ths`、`akshare`、`eastmoney_via_akshare` 都路由到名称接口。
- `sector_akshare.py:get_sector_stocks_akshare()` 实际调用东方财富目录，按名称完全相等查找 BK 代码，再获取成分。AKShare 是适配库，不能代表独立的板块分类体系。
- `_fetch_named_em_stocks()` 每次调用均从第一页读取目录，重复分页使请求数放大。145 次不能全部解释为重试。
- 同名匹配成功只能证明名称一致，不能证明同花顺和东方财富成分集合一致；因此不仅失败的 20 个板块需要处理，成功跨源匹配的板块也需核查资格。
- `source_health.py` 将映射缺失/歧义作为单项问题，计入失败但设为 `healthy`。保留继续扫描的意图合理，展示语义及混合故障状态需要完善。
- 当前名称缓存允许保存实际来自东方财富的成分；成功请求用 `as_of_date` 或系统日期赋予 `data_date`。缓存身份和日期证据必须同时审计，不能通过改标签将请求日期变成行情日期。

## 范围与原则

本轮改动板块身份、成分路由、目录共享、缓存证据和审计。保持推荐评分、市场档位、板块持续性来源要求及买点门槛，不通过放宽门槛补足推荐数量。历史正式推荐快照不覆盖。

优先使用与排行相同分类体系的成分。没有可靠同源接口时明确缺失；不预设某个 AKShare 接口当前存在或可用。禁止模糊匹配自动升级、“白酒”直接等同某个更宽行业、行业与概念互换、一对多映射静默合并。纯性能优化不能提高数据资格。

## T1：明确提供方身份与路由合同（P0）

涉及：`scripts/fetchers/sector_akshare.py`、`scripts/fetchers/sector_data.py`、`scripts/scans/stock_scanner.py`、`scripts/scans/daily_candidates.py`。

1. 先检查本地实际适配库与现有 fetcher，列出同花顺行业/概念、东方财富行业/概念可用的排行和成分能力。必要时以官方文档及少量只读请求核实接口，不把函数名称当作来源证据。
2. 定义稳定身份：分类提供方、板块类型、提供方真实代码；名称只作展示或提供方内解析。AKShare 单列为适配方式。排行序号永远不能当作板块代码。
3. 东方财富 BK 身份直接走 BK 成分接口；同花顺身份走经核实的同源成分接口；旧 `akshare` 身份根据原始来源证据解析，无法确定则标记身份未知，不猜测来源。
4. 若同花顺同源成分无法可靠获取，可继续输出观察方向；如选择东方财富完成扫描，应重新取得东方财富排行并走完整资格流程，不能沿用同花顺热度/持续性给东方财富成分背书。不得在单只股票层面静默切换板块宇宙。

验收：四类身份路由正确；旧序号被拒绝；同名不同来源及行业/概念不会混用；同源不可用时仍可生成明确降级结果。

## T2：跨源映射与缓存资格（P0）

1. 将跨源映射作为显式回退，不再用同名命中代表等价。映射记录包含两端身份、关系类型、核验来源、核验时间/有效区间、版本与状态。
2. 默认跨源记录只能作相关方向的观察旁证。只有具备可审计等价证据且覆盖本轮依据日的映射，才可参与成分资格；关系为近似、包含、一对多、歧义或未知时不得继承原板块资格。
3. 实施第一批不要求填满映射表。优先核查本次缺失的白酒、证券、中药、文化传媒等；不能确认等价时保留 unresolved，并给出具体失败原因。同名成功的跨源记录执行同样检查。
4. 缓存按实际分类提供方、板块类型、真实 ID 与 schema 版本隔离；记录排行来源、成分来源、跨源关系和真实日期证据。旧名称缓存保留可读，但未经核验不能自动升级为同源有效数据；不原地改写旧证据。
5. 分开成分归属依据日、个股行情日期与抓取时间。请求参数 `as_of_date` 不能证明历史归属或报价日期；当前成分不能伪装成历史成分。延续已有过期缓存观察规则。
6. 主板块重绑定和多归属合并必须保留这些证据，不能在合并后洗掉跨源/过期状态。

验收：同名不同分类、失效映射、一对多、缺日期、旧缓存和多归属重绑定均不误晋级；真实有效同源成分仍能通过原质量门槛。

## T3：共享目录与请求预算（P1）

1. 每轮扫描创建按提供方和行业/概念隔离的目录上下文，按需加载并由各扩池批次共享；优先复用本轮已取得且完整的同源目录。
2. 并发首次加载只执行一次，其他线程复用结果；上下文限定本轮生命周期，不能用无期限进程全局缓存混用不同日期。
3. 目录必须完成分页且验证结构，才能认定名称不存在。分页失败、超时、权限错误分别记录，不能伪报 `sector_mapping_missing`。明确失败后按预算有限重试，不对每个板块重复加载整个失败目录。
4. 目录请求遵守现有总 deadline、超时与重试限制。缓存-only 调用不得隐式发目录请求。
5. 新增目录实际请求数、成分实际请求数、重试数及目录复用次数。共享目录请求只计一次；明确旧 `provider_attempts` 的兼容含义，不能复制到每个逻辑结果造成重复计数。

验收：40 个板块并发/多批展开只触发每类目录的一次完整加载周期；分页与重试次数可对账；目录后续页失败不被当作名称缺失；单轮结束后下一轮重新按有效性规则读取。对比同一固定夹具优化前后请求数量，不承诺将本次 145 次机械降到某个值。

## T4：区分传输健康与业务覆盖（P1）

涉及：`scripts/core/source_health.py`、`scripts/scans/daily_candidates.py` 及报告审计输出。

1. 映射错误继续计入业务失败，且不单独触发全源熔断；保留其他板块继续请求的能力。
2. 新增传输/接口状态、映射失败数、成分可用覆盖率与业务降级原因。旧 `state` 保留兼容并说明含义；MD、HTML、JSON 从同一个完成后的审计对象生成。
3. 检查混合事件序列：映射缺失不能无条件清除真实接口故障。区分“本次目录 HTTP 成功”和“整体成分接口恢复”，只有对应的成功证据才能恢复相应状态。
4. 报告明确写出“接口可访问；成分仅覆盖 20/40；20 个映射未解决”等结果。失败明细包含原提供方、类型、名称/ID、失败阶段及原因；尝试覆盖与可用覆盖分别显示百分比，零分母显示不适用。

验收：纯映射失败不熔断但业务 degraded；真实网络故障仍按既有阈值降级/熔断；网络故障后出现映射缺失不错误恢复；最终回退成功不重复计为最终缺失。

## 验证、顺序与交付

实施顺序：T1 身份与能力核实 → T2 资格/缓存 → T3 目录共享 → T4 审计。每步先完成相关固定夹具，再做下一步。能力核实结果应写回本计划，不能把未验证接口当作已经可用。

重点测试文件：`test_stock_scanner.py`、`test_daily_candidates.py`、`test_daily_recommendation_performance.py`，以及实施时定位的板块 fetcher/缓存测试。新增入口集成用例，模拟同花顺排行、东方财富同名/异名目录及部分回退，检查最终分桶、覆盖率、请求计数和缓存身份，而非只验证 helper 返回值。

修改 Python 脚本前说明影响范围；每个脚本交付批次运行相关测试和仓库两项门禁：

```bash
python3 .claude/skills/stock-trend/tests/test_stock_trend.py
python3 .claude/skills/stock-trend/tests/test_golden.py --diff
git diff --check
```

不为消除失败而更新 golden。真实联网烟测在逻辑验证后使用少量代表板块，标注日期、来源、失败及缓存状态；全量候选报告另行按任务范围执行，不覆盖既有正式历史。同步技能、规格与模型/缓存版本说明；若跨源资格收紧改变候选集合，明确属于预期行为变化。

完成标准：板块身份不串源、未经验证的跨源成分不能获得推荐资格、目录请求按轮共享、计数可对账、映射问题与接口故障可区分，相关测试及两项门禁通过。成分覆盖率提高是运行验证结果，不以“必须达到 100%”作为放宽规则的理由。

风险：严格身份核查可能使目前同名匹配成功的部分板块降为观察，短期覆盖率可能降低；真实同源接口可用性也可能限制恢复。按提供方隔离改动以便回滚，回滚不删除缓存证据或历史快照。

本计划及相关分析仅供学习参考，不构成任何投资建议。股市有风险，投资需谨慎。
